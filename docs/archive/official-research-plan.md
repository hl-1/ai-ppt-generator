# 官方资料查询与规划书生成设计

状态：设计预览，尚未接入生产链路。示例主题为“春节去北京旅游规划”。

## 目标与边界

让主题生成先补齐约束、查询可信来源，再生成可追溯的规划书。沿用现有 FastAPI、ARQ、PostgreSQL、LangGraph 和 PPTX 导出，不另建一个生成系统。

第一版覆盖北京旅游规划的官方公开资料：景区预约规则、开放公告、节庆公告和交通服务入口。适配器可扩展到其他城市和主题。

官方公告能证明规则，不能证明用户预约成功。实时余票、酒店房价、地图路线和天气分别需要相应服务的 API 授权；未接入时显示待查询或估算，不用网页搜索结果代替实时库存。

## 用户流程

1. 输入主题，补充出发地、目的地、出行日期、天数、人数、儿童或老人、总预算和偏好。日期缺失时生成建议草案，不能输出确定的假期安排。
2. 启用官方资料查询。展示查询阶段、已找到的官方入口、覆盖的事实类型及缺口，允许重查失败来源。
3. 查看规划书：每天的游览顺序、交通方案、预约前置条件、费用状态和天气或预约失败的替代方案。
4. 从任意关键事实打开其来源详情：官网 URL、原文摘录、发布时间、适用日期、查询时间和验证状态。
5. 完成预约、车票及住宿等人工待办。用户完成状态独立于官网规则验证状态，不由模型推断。
6. 导出文字规划书及 PPTX。资料不完整时导出明确标识的草案；无关键缺口时才显示“资料核实完成”。

## 后端链路

```text
完整主题 + 结构化要求
    -> 生成查询清单（主题、日期和城市决定范围）
    -> 搜索官方域名与官方公告
    -> 抓取、缓存原文
    -> 抽取结构化事实及逐条原文引用
    -> 验证官网归属、原文匹配和适用时间
    -> 生成规划书并校验可执行条件
    -> 用户确认大纲
    -> 用同一份事实包生成 PPT 正文和文字版
```

检索与抓取使用可替换的服务适配器。首选通过 HTTP 调用 Firecrawl 搜索及抓取服务；生产部署需要单独配置服务凭证，桌面会话里的 MCP 权限不能直接提供给线上应用。地图、天气和库存接口可按阶段接入。

模型负责生成查询清单、整理原文和编排行程。最终来源身份、引用原文匹配、日期区间及缺失字段由后端校验。模型自行给出的链接和发布日期不能作为验证证据。

## 数据结构

新增 `project_research_runs`：项目、任务 ID、请求指纹、状态、阶段、开始及结束时间、错误码、资料包版本。

新增 `research_documents`：项目、来源类别、官方发布者、URL、规范 URL、标题、抓取时间、正文哈希、原文存储键、可验证的发布时间和适用时间、抓取状态。

新增 `research_facts`：文档 ID、事实类型、结构化值、单位、适用地点、原文摘录、适用日期、验证状态和过期时间。验证状态取 `verified / partial / conflicting / unavailable / expired`；有官方出处但没有当年适用范围的资料是 `partial`。

项目增加 `planning_requirements`、`research_enabled`。规划书包含 `days`、`transport`、`cost_items`、`booking_tasks`、`alternatives`、`fact_refs` 和 `unresolved_items`。费用逐项标为官方规则价格、供应商报价、估算或待询价，并保留价格条件和有效时间。

完整主题、要求、资料包版本一起进入现有 `project_input_signature`。逐页生成直接读取对应版本的事实包，不能在每页并发时分别查询出不一致的规则。

## 拟定接口与改动位置

| 位置 | 改动 |
| --- | --- |
| `schemas/project.py`、`models/project.py` | 增加结构化规划条件及查询开关；新增数据库迁移 |
| `services/research.py`、`research/providers/` | 官方来源发现、抓取、缓存、事实校验和缺口管理 |
| `POST /projects/{id}/research/generate` | 启动查询任务，返回 job ID |
| `GET /projects/{id}/research` | 当前资料版本、文档、事实和缺口 |
| `GET /projects/{id}/research/events` | 沿用 SSE，显示查询和校验进度 |
| `POST /projects/{id}/research/retry` | 重试指定失败来源；执行来源权限和请求指纹检查 |
| `worker/tasks.py` | 大纲生成前执行独立查询阶段；超时和取消必须落库 |
| `llm/base.py`、`llm/topic.py` | 增加已核实事实、部分核实事实和未解决约束；引用只能使用资料包中的 ref |
| `worker/deck_tasks.py` | 传递同一版本的资料包和完整主题给每页 |
| `POST /projects/{id}/plan/generate` | 生成结构化规划书，绑定资料版本 |
| `GET /projects/{id}/plan` | 规划书、资料引用、待办及过期状态 |
| `PATCH /projects/{id}/plan/tasks/{task_id}` | 保存用户自行确认的预约、购票等状态 |
| `GET /projects/{id}/plan/export` | 第一版文字版，后续增加 PDF；PPTX 继续使用现有导出链路 |
| `frontend/src/pages/CreatePage.tsx` | 补充规划要求，默认保留原始主题；启用查询 |
| 项目详情页 | 官方资料、来源详情、逐日行程、预算状态和待办视图 |

## 校验与失败处理

- 按主题配置官方发布者和域名；检查目标 URL、重定向和抓取页面归属。网页正文是外部资料，不能当成工具指令。
- 精确价格、预约时限、开放日期必须匹配来源原文，并且适用于出行日期。往年春节公告不能支持当年活动。
- 发布日期未知时保留未知；查询时间仅证明什么时候抓取，不能替代发布日期或当年适用范围。
- 同一天不安排明显不相容的景区与预约时段。没有地图服务时交通时长标为估算，不能宣称路线已经校验。
- 热门预约失败、低温或雨雪应有可替换活动。预算缺价时显示已确认小计和待报价项目，不展示伪完整总价。
- 每个查询来源设置超时和重试上限；整份任务设置总预算。部分失败返回缺口，整体失败可重试，不能无限显示生成中。
- 复用现有 job ID 和 revision 检查：条件变化后迟到结果不覆盖新结果。查询失败不回填模拟数据。
- 日志只记录项目 ID、任务 ID、阶段、来源域名、耗时、数量和错误码；原文、完整提示词和凭证不进入普通日志。

## 分阶段实现

1. 官方资料最小闭环：结构化条件、检索适配器、来源和事实表、资料页、来源引用、大纲和正文事实传递。
2. 可执行规划书：逐日规划校验、预约待办、费用状态、替代方案、文字版导出、资料过期刷新。
3. 实时服务：地图、天气、酒店及交通报价，按已获得的 API 权限接入；可选出发前再核查。

优先实现前两阶段。没有检索服务凭证时，界面必须显示“查询服务未配置”，不能把主题模型输出显示成已查证结果。

## 验收用例

- 用“春节去北京旅游规划”验证全过程，输出内容覆盖行程、预约、交通、住宿、费用状态和备选方案。
- 混入往年庙会公告，结果应保留当年缺口，不形成确定活动安排。
- 来源缺失、冲突、抓取超时、查询取消及资料过期均有明确状态和重试路径。
- 将出行日期和天数改动后，旧查询或规划书不得显示为当前条件下已核实。
- 任意精确预约时间或价格都可打开真实来源；模型给出但原文不存在的值必须被拒绝或标为待核实。
- 规则已核实和用户预约已完成分别保存。未预约故宫时，规划书仍显示预约前置条件和替代方案。
- 前端桌面和移动端无文本遮挡；逐日切换、来源详情、重试、待办和文字版均可使用。
